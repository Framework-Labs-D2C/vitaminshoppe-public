03 — Fields

What a merchandiser fills in

Generated from _schema.ts, in the order Amplience shows them.

FieldTypeConstraintsDescription
eyebrow
Label		 string max 30 A short label in the chip above the heading, e.g. "Bundle & Save". Type it in sentence case — unlike other modules this one prints it exactly as you write it. The chip's colour, size and information icon are fixed and cannot be changed. Keep it to two or three words: the chip hugs its text and is capped at 30 characters, and past about 20 it stretches most of the way across the column and stops reading as a label. Formatting: **bold**, _italic_, and ~12~ for subscript. A registered mark (®) is raised automatically, and a plain asterisk is never formatting. Leave empty to hide the chip.
heading
Heading		 string required max 60
min 1		 The bundle's name, e.g. "BodyTech Recovery Stack". It sits beside the photograph on desktop in a column a little under half the page, so anything past about 30 characters wraps to a second line and pushes the products down. Wrap words in _underscores_ for italic and **double asterisks** for bold. Write ~12~ for subscript; a registered mark (®) is raised automatically, and a plain asterisk is never formatting.
headingLevel
Heading level		 string h1 · h2 · h3
default "h2"		 Choose h1 only if this module is the first thing on the page and no other h1 exists. Otherwise leave it as h2 — two h1s on one page hurts SEO. Choose h3 when the module sits underneath a section that already has an h2, so the page's heading order stays unbroken. This changes nothing you can see: the size is set separately below.
headingSize
Heading size (desktop / mobile)		 string 64px / 38px · 56px / 34px · 48px / 30px · 36px / 24px · 28px / 20px · 20px / 16px
default "36px / 24px"		 A fixed pair from the TVS type scale — the first size applies from tablet up, the second on phones. 36px / 24px is the design. The heading shares its column with the product list, so a larger pair wraps sooner and pushes the Add to Cart button further down.
headingFont
Heading font		 string Lato · corisanderegular · Fields
default "Fields"		 Fields is the serif this module is designed in and is the default. It is not yet installed on vitaminshoppe.com, so until it is, the heading falls back to Georgia — still a serif, but not the exact drawn face. Pick Lato if you would rather the heading match the rest of the site exactly than approximate the design.
image
Bundle photo		 string required min 1 Full URL of the photograph beside the products. jpg, jpeg or png. It fills the left half of the module on desktop and is cropped to fit, so keep the products near the centre — the edges are trimmed at narrow widths.
imageAlt
Bundle photo alt text		 string required min 1 Describe what the photograph shows, e.g. "Recovery Pep and Muscle Growth Peptide tubs stacked on gym weights". Required for accessibility. Do not write "image of" — a screen reader already says that.
imageMobile
Bundle photo (mobile)		 string max 500 Full URL of the phone crop, which is wider than it is tall. Falls back to the desktop photograph when empty, cropped to the shorter shape.
imageAltMobile
Bundle photo alt text (mobile)		 string max 300 Only needed when the phone crop shows something different. Leave empty to reuse the desktop alt text, which is also what happens if no mobile photograph is set.
priority
Prioritise image loading		 boolean default false Switch on when this module is the first thing on the page, so the photograph loads immediately instead of lazily.
skus
Products (SKU ids)		 array required The products in this bundle, in the order you list them. Enter TVS SKU ids exactly as they appear on the product page, e.g. VS-4612. Each row's image, name and price is pulled live from the product record, so there is nothing else to fill in here. A bundle is sold as one set, so it is all-or-nothing: if any of these SKUs is out of stock, or no longer exists, the whole module hides itself rather than offering an incomplete bundle.
ctaStyle
Add to Cart button colour		 string dark · light · outline
default "dark"		 Dark is #0458AD with white text and is the right choice almost every time, because the button sits on a white card. Light is white with #0458AD text and a thin #0458AD outline — it needs a dark surface behind it to be visible, so on the white card it reads as a weaker second choice rather than the main action. Outline is transparent with a black edge and black text, which also reads on the white card and is quieter still. Here it is the only button in the module and it spans the full width of its column, so Dark is almost always right. The button's wording is fixed and shows the bundle's price, so there is nothing else about it to set.
showPromotionSummary
Show promotion summary		 boolean default true Shows the breakdown under the Add to Cart button: how many products the bundle holds, what they come to, the promotion and its saving, and the subtotal. Switch off to show the button alone. The breakdown also stays hidden whenever the discount below is empty or zero, because there would be no saving to describe.
promotionName
Promotion name		 string max 40 What the offer is called, e.g. "Buy 2 get 1 50% off". The module writes the saving after it, so type the offer's name only — no colon and no amount. It shares one highlighted line with that saving and is capped at 40 characters; past about 30 the line wraps to two and the highlight grows with it. Formatting: **bold**, _italic_, and ~12~ for subscript. A registered mark (®) is raised automatically, and a plain asterisk is never formatting.
discountValue
Discount		 number How much the bundle saves, as a number only — write 50 rather than 50% and 12.99 rather than $12.99. Choose below whether that is a percentage or an amount in dollars. Leave it empty, or set it to zero, and the promotion summary disappears and the button shows one plain price with nothing struck through. A saving larger than the bundle costs is capped at the bundle's own price rather than going negative.
discountUnit
Discount type		 string % off · $ off
default "% off"		 Whether the number above is a percentage of the bundle's total or a flat amount off it. A percentage keeps working when a price changes; a flat amount does not, so check it after any repricing.
sectionId
Section ID		 string max 50
^[a-z][a-z0-9-]*$		 A name for this specific bundle, used for two things. The Sticky Anchor Navigation links to a module by this name, so a bundle that should appear in that bar needs one. A link anywhere on the site can also jump straight here by ending the URL with # and this name, e.g. #recovery-stack. Use lowercase letters, numbers and hyphens, start with a letter, and make it unique on the page — two modules sharing an ID will break both the jump link and the nav bar.

User requirement

09 — Open comments

Open comments

The bundle photograph is not in the Admin requirement table — unanswered 2026-08-10

unanswered 2026-08-10

Both frames draw a large lifestyle photograph as the section's left half on desktop and its second element on mobile, and it is clearly authored rather than pulled from a SKU: it shows two products staged together on a coloured ground. The Admin requirement table lists Label, Heading, SKU Selection, Product Card, Add to cart button and Promotion Summary, and no image field among them. We are adding an image and alt-text pair, plus an optional phone crop, because the section cannot render its own design without one. Please confirm the field set, and confirm whether the mobile crop is a separate asset or the desktop one re-framed.

Which price the rows and the total each use — unanswered 2026-08-10

unanswered 2026-08-10

The spec asks for two different prices in two adjacent rows. Product Card says "Price (only final price price)", so each row shows the price actually charged. Add to cart button says "Total price is dynamically calculated by adding SKU's compare at price", so the struck total sums the compare-at price instead. In the design every row reads $25.99 and the struck total reads $77.97, which is exactly three times $25.99 — so the drawn example has compare-at equal to final price and cannot distinguish the two readings. Taken literally the section would show three final prices that do not add up to the total beside them whenever anything in the bundle is on sale. We have implemented the literal reading and flagged it here; if the intent is that the total sums the same price the rows show, that is a one-line change.

The struck price is larger than the price charged on mobile — unanswered 2026-08-10

unanswered 2026-08-10

On the mobile button 18228:432969 the struck was-price is 18px and the payable price is 16px; on desktop 18228:432891 both are 16px. Drawing the price the customer does not pay larger than the one they do is unusual enough that we read it as a drafting slip and matched the desktop treatment on both breakpoints. Confirm, or tell us the mobile emphasis is deliberate.

What the info glyph in the label chip does — unanswered 2026-08-10

unanswered 2026-08-10

The label chip carries a 16px info-circle after its text on both frames. Nothing in the spec mentions it and no tooltip, popover or target is drawn anywhere in the file. It currently renders as decoration with aria-hidden. If it is meant to disclose the promotion's terms, it needs both the copy and a disclosure pattern, neither of which exists yet.

Whether the promotion discount is ever validated against the cart — unanswered 2026-08-10

unanswered 2026-08-10

The discount is authored: the merchandiser types a promotion name and either a percentage or a dollar amount, and the section computes the subtotal from it. Nothing checks that a matching promotion actually exists in TVS's promotion engine, so a bundle can advertise a saving the cart will not apply. TVS-Common exposes no promotion API to us, so we cannot verify it from the front end. Is there a process that keeps the authored discount and the real promotion in step?

Should the summary amounts be right-aligned — unanswered 2026-08-10

unanswered 2026-08-10

Every visible row of the promotion summary carries a hidden second text node anchored to the row's right edge, and each row is drawn as a flex container with a gap. The visible state collapses to one left-aligned string, which is what we built, but the reserved structure is plainly a label-on-the-left, amount-on-the-right row. That reading also explains the promotion row, which is a full-width tinted band with its text bunched at the left — as a two-column row it would be balanced, and as drawn it reads as a highlighter stroke across the column. Should the three rows put their amounts on the right?

Heading typeface — unanswered 2026-08-10

unanswered 2026-08-10

The design sets the heading in Fields Bold, and the Figma node's own family token disagrees with the applied style: the token dereferences to Lato while the rendered style is Fields. Fields is not loaded on vitaminshoppe.com today, so a heading set in it falls back to a system serif. This is the same question raised on the Product Carousel FSD and has the same answer here: the field offers Fields and defaults to it for this module, because unlike the carousel the serif is the whole character of the drawn design. Is Fields being added to the site's font stack, and on what timeline?

Impression tracking has no agreed event — unanswered 2026-08-10

unanswered 2026-08-10

"Other requirements" asks for automated impression tracking on viewport entry. No Platter module implements it yet, because no event name or payload has been agreed for any of them; the question is still open on the Slim Hero Banner FSD. Click tracking ships here using the shared raiseEvent('ItemClick', …) payload.

10 — Deviations

Deviations

The total sums the price shown on each row, not the compare-at price

Built

The spec says the total is "calculated by adding SKU's compare at price" while the rows show "only final price". The design's own arithmetic contradicts the wording: three rows at $25.99 sit under a total of $77.97, which is the sum of the prices on screen. We add up the prices on screen.

The literal reading was built first and rejected on the render. Whenever anything in the bundle is on sale the two bases diverge, and the module then prints three prices that visibly do not add up to the total directly beneath them — a pricing claim a shopper can check in their head and find wrong. The open comment above stays open; if the client confirms the compare-at basis it is a one-line change in normalize().

The bundle photograph is a field the spec does not list

Built

image and imageAlt are required, imageMobile and imageAltMobile optional, spread from the shared vocabulary. The design cannot render without them and the Admin requirement table has no image row — see the open comment. This is the first section to consume the content-imagery mobile pair.

Heading level, size and typeface, and Section ID, are merchandiser settings

Built

The spec lists only "Admin can edit the bundle heading" and no anchor requirement at all. These four fields exist on every other Platter section, and heading level in particular is what keeps the page's heading order intact when a bundle sits under another module. Adding them keeps one vocabulary across the CMS rather than making this form the exception. The typeface defaults to Fields here rather than Lato, because the serif is the character of this design rather than an accent.

The label chip is not uppercased

Built

The shared eyebrow field is described as uppercasing itself, and every other section that uses it does. This design draws the chip in sentence case, so the uppercase class is simply absent here. The uppercasing was always markup rather than a property of the field, so nothing about the shared field changed; its description in this section says which behaviour applies.

The Add to Cart button wears the shared Platter button

Built

Figma draws this button 55px tall on desktop and 41px on mobile, with 16px text on both and no letter-spacing. components/button.css is the TVS button every other Platter module uses, and it resolves to about 50px and 43px with the shared 0.04em tracking. The section takes the shared skin and sets only --plx-button--font-size-mobile, the documented public knob, so the mobile label matches the design's 16px. The remaining few pixels of height are the price of one button across the whole component set, which is the trade sections/CLAUDE.md makes deliberately — a per-section box would be the loose button fields that file forbids.

Section padding is on the inner wrapper, not the section root

Built

§ Root structure puts padding on the section root. Here the spec says an out-of-stock SKU hides "the entire section", and the element that hides is the wrapper inside the root — the root carries x-data="props" and cannot read the scope that knows whether to hide. Padding on the root would therefore leave a 96px empty band where the module used to be. The padding moved to the wrapper so that hiding removes all of it. The wrapper's max-width is 1512 rather than 1416 for the same reason: Tailwind is border-box, so the inline padding sits inside the cap and the composition still measures 1416.

The drawn sizes arrive at md, the two columns at xl

Corrected 2026-08-10

Two breakpoints, each governing one thing: every drawn size steps in at md (768), and the layout becomes two columns at xl (1280).

The design is drawn at 1512 with a 593px text column beside a 759px photograph, and fixed columns cannot simply be applied earlier. Between md and xl the module is therefore a single centred column capped at 600px — 568px of content, within 4% of the drawn 593px text column — so every drawn size fits there exactly and the band reads as the desktop design stacked, not as a stretched phone layout. From xl the columns are fractional, giving 491px of text at 1280 and the drawn 593px at 1512.

The columns deliberately do NOT arrive at lg, which sections/CLAUDE.md § Breakpoint would normally prescribe. The arithmetic there does not survive: at 1024 the fractional split leaves the photograph 424px wide in a column roughly 636px tall, so a landscape hero would be cropped into a portrait slot. That section asks for the arithmetic to be checked at the flip point and the flip moved where it does not fit, which is what this is.

First built with the sizes at xl and the columns at lg. The in-between review at 768 caught the consequence: the heading and the shared button already switch at 768, so that combination rendered a 36px desktop heading and a desktop-boxed button above a product list still drawn for a 343px phone. The underlying error was assuming the single-column band was narrow like a phone, when the 600px cap in fact makes it wider than the two-column text column at lg — the column width ran 343, 568, 379, 491, 593 and was not monotonic. It now runs 343, 568, 491, 593.

The photograph takes its height from the text column

Built

From xl the photograph spans both grid rows and stretches to whatever the text column comes to, and it is object-cover, so it crops rather than distorts. Turning the promotion summary off removes about 105px from that column and the photograph crops that much harder. The design's causality is the reverse — the text column is height-matched to the photograph — so a height floor was considered and deliberately not added: every candidate value is arbitrary, and the drawn 654px would make the photograph taller than it is wide at 1280. Raised at review and left as it is by Felix's call.

The band between 1024 and 1279 keeps the single column

Built

A consequence of the breakpoint choice above, recorded because it is visible rather than because it is wrong. At 1279 the module is a 568px column in a 1279px viewport, so roughly 355px of the page is empty on each side. The alternative was two columns from lg, which fills the width but drops the text column to 379px against the drawn 593, clamps the product names harder, and stops the two columns ending level. Raised at review with both renders; the single column was chosen because every drawn size stays at the measure it was drawn for.

The product thumbnail is part of the row's link

Built

The design draws no link on the thumbnail, which leaves the product name's text line — 24px tall, with rows 12px apart — as the only target in the row. At 768 the likely device is a tablet in portrait, where a shopper will tap the product image and get nothing. The thumbnail is wrapped in an anchor to the same destination, tabindex="-1" and aria-hidden="true", so the row still contributes exactly one link to the tab order and to a screen reader. This is the pattern blocks/product-card already uses for its own image. It also gives the row a 92px target in place of a 27px line of text.

The header is hoisted above the photograph on mobile

Built

The two frames are not a reflow of one source order. Desktop is the photograph beside a column holding the header, the products, the button and the summary; mobile puts the header first, then the photograph, then everything else. A flex container that only flips its direction cannot produce both. The section root is therefore a grid: DOM order is header, photograph, content, which is the mobile order, and explicit col-start / row-start placement puts the header back into the right-hand column at xl. No other Platter section reorders a child between breakpoints, so this is the first.

An unresolvable SKU hides the bundle, as an out-of-stock one does

Built

The spec says the section hides when any included SKU is out of stock. It does not say what happens when a SKU no longer exists — the Product Carousel drops that card silently, which is right for a carousel and wrong here. A bundle is priced and sold as a set, so a missing product would mean advertising a total for goods the shopper cannot buy. Any SKU that fails to resolve hides the whole module, and the failure is logged to the console.

Product names are clamped to two lines

Built

Both frames draw the name over two lines, and the sample copy happens to fill exactly two at the drawn width. A longer name would push the row past the photograph beside it and open a gap under the summary, so the name is clamped to two lines with an ellipsis. The mobile frame already specifies that clamp; the desktop frame does not, and this applies it there too.

The mobile struck price matches the desktop treatment

Built

See the open comment. The mobile button draws the struck was-price at 18px against a 16px payable price. Both render at the shared button size here, as they do on the desktop frame, rather than emphasising the price the customer is not charged.

States absent from the design

Built

Figma draws no hover, focus, disabled, loading or error state anywhere in this section. Accessibility is a delivery requirement, so the implementation adds a visible focus ring on the product links, skeleton rows while the bulk request is in flight, a disabled button until prices are known and while an add is running, a polite live region announcing that the products have loaded, and a second one announcing the result of an add. Both live regions stay silent on the paths that remove the module, because there is nothing left on screen to describe.

Impression tracking is not implemented

Not built

See the open comment. Click tracking ships, using the shared raiseEvent('ItemClick', …) payload with moduleTitle. Impression tracking has no agreed event name or payload for any Platter module yet, so it is deliberately left out rather than invented here.

Platter component

Main Buy Box and Sticky CTA Bar

One section carries two client specs, because the sticky bar is a scrolled state of the buy box rather than an independent module: it shows the same SKU, the same selected variant and the same resolved price, and both add the same line to the cart. Splitting them into two content types would make a merchandiser configure one product twice and keep the two copies in step by hand.

03 — Fields

What a merchandiser fills in

Generated from _schema.ts, in the order Amplience shows them.

FieldTypeConstraintsDescription
heading
Heading		 string max 90
min 1		 An optional headline above the whole module, e.g. "Build your stack". Neither design has one, so leave it empty unless the page needs the buy box introduced — the module reads perfectly well starting at the product name. Wrap words in _underscores_ for italic and **double asterisks** for bold. Write ~12~ for subscript; a registered mark (®) is raised automatically, and a plain asterisk is never formatting.
headingLevel
Heading level		 string h1 · h2 · h3
default "h2"		 Where this module sits in the page's heading order. It applies to the headline above when you have written one, and to the product name when you have not — the product name is always a heading, so a screen-reader user can find the module either way. Choose h1 only if this is the first thing on the page and no other h1 exists. This changes nothing you can see: the size is set separately below.
headingSize
Heading size (desktop / mobile)		 string 64px / 38px · 56px / 34px · 48px / 30px · 36px / 24px · 28px / 20px · 20px / 16px
default "36px / 24px"		 A fixed pair from the TVS type scale for the optional headline above the module — the first size applies from tablet up, the second on phones. It does not change the product name, which is fixed at the design's 28px / 20px so the two never compete. Has no effect while the headline is empty.
headingFont
Heading font		 string Lato · corisanderegular · Fields
default "Lato"		 Lato is the site's heading typeface and the safe choice. Corisande is its body typeface — pick it when the module needs to sit closer to surrounding editorial copy. Fields is the serif used in the newer designs; it is not yet installed on vitaminshoppe.com, so until it is, headings set in Fields fall back to Georgia and will not look identical on every device.
body
Description		 string max 160 An optional sentence under the headline, for a campaign line or a shipping promise. Neither design has one. It sits above the product, so anything long pushes the price and the add-to-cart button down the page. Formatting: **bold**, _italic_, and ~12~ for subscript. A registered mark (®) is raised automatically, and a plain asterisk is never formatting, so a footnote marker like 20%* is safe. Leave empty to hide it.
variants
Products and variants		 array required Every SKU this module can sell, one row each, in the order you list them. Drag a row to reorder it. A single row means a product with no choices and no pills at all. Everything shown — name, image, price, promo, rating, purchase limit and subscribe-and-save terms — is pulled live from each SKU, so the only things to write here are the option names a shopper picks from. Enter one row per real, buyable combination: a flavour in three sizes is three rows, not one. The first row is what the module shows when the page loads.
optionOneLabel
First option name		 string required max 24
default "Flavor"		 The label above the first row of pills, naming what the shopper is choosing — "Flavor" in the design. Use the word on the packaging rather than a generic one, so "Strength" or "Scent" where that is what varies.
optionTwoLabel
Second option name		 string max 24 The label above the second row of pills — "Size" in the design. Leave it empty when the product has only one kind of choice, and the second row disappears along with it. Filling this in while every variant leaves its second value empty shows a label above nothing, so set the two together.
showSubscription
Offer subscribe and save		 boolean default true Shows the subscribe-and-save panel above the add-to-cart button, with the delivery frequencies and the discount the product itself offers. Switch it off to sell the product one-time only. It also hides itself for a SKU that is not enrolled in Auto Delivery, so leaving it on is safe for a mixed range — a product without a subscription simply shows the one-time row.
showStickyBar
Show the sticky bar		 boolean default true Brings a slim bar down from the top of the screen once the shopper scrolls past the buy box, carrying the product image, its name, the selected variant, the price and the same add-to-cart button. It follows whatever the shopper has chosen above, so it never adds a different SKU to the cart than the one on screen. Switch it off on a page where something else is already pinned to the top and the two would stack.
showPromoBadge
Show promo badge		 boolean default true Shows the offer badge beside the price, e.g. BOGO, and the note behind its info glyph. The wording comes from the product record rather than from here, and the badge hides itself on a product with no offer running, so this is a way to keep the module quiet during a campaign you do not want highlighted rather than a way to write one.
priority
Prioritise image loading		 boolean default false Switch on when this module is the first thing on the page, so the product image loads immediately instead of lazily.
sectionId
Section ID		 string max 50
^[a-z][a-z0-9-]*$		 A name for this specific module, used for two things. A link anywhere on the site can jump straight to it by ending the URL with # and this name, e.g. #buy-box. Page-level CSS can also target this one module rather than every Buy Box. Use lowercase letters, numbers and hyphens, start with a letter, and make it unique on the page — two modules sharing an ID will break the jump link. Leave empty if you need neither.

06 — User requirement

User requirement

From the Main Buy Box page:

  1. User can select a variant (flavor/size) when the assigned SKU has related variants; selecting a variant swaps price, image, and availability — mirrors PDP variant-switch behavior.
  2. User can toggle between one-time purchase and subscription, where enabled (scope pending).
  3. User can adjust quantity; if the SKU carries a purchase limit, the user sees a limit-reached warning message.
  4. User can add the item to cart — identical behavior to the PDP, except for delivery-option selection.

From the Sticky CTA Bar page:

  1. User can click the persistent CTA from any scroll depth once they've scrolled past the Main Buy Box.
  2. The bar stays pinned to the top of the viewport on both desktop and mobile.

Which viewport edge the sticky bar pins to — answered 2026-08-31

answered 2026-08-31

Neither sticky frame carries a viewport, a constraint annotation or a note. The drop shadow points downward in both, which suggests the bar sits at the top, but that is inference from one property. Subscription toggle feasibility — unanswered 2026-08-31

unanswered 2026-08-31

Answering the first of the Aug 6 open items, which asks us to verify it. It is feasible: getProductPDPDetails carries subscribeSaveDiscount, adpDiscountPercentage and, under bccSkuAttrtes.bccSku, both listOfAutoDeliveryFrequency and recommendedFrequency, and _vsiMicroFE.cart.addToCartADP takes autoDelivery and frequency. Two things in the contract are unresolved rather than hard. The ADP example passes storeId: "894" with no explanation, no lookup endpoint, and no statement of whether a DTC add needs it at all. And frequency is documented as a number while every response that supplies the list returns strings, with the example passing a 120 that appears in neither sample list. We can build the toggle; we cannot guarantee an ADP add-to-cart succeeds until those two are answered, so please treat descoping as a decision about risk rather than about capability.

Switching a variant without leaving the landing page — unanswered 2026-08-31

unanswered 2026-08-31

Answering the third Aug 6 open item. It is possible, and the mechanism matters because it sets what a swap can and cannot change. sku.variantFilters is the only API path carrying variant attributes: variantAttributes.attributeOne and attributeTwo give the two axes and their value lists, and variantSkus[] gives each combination its own skuId, price and burstMessage. So price and availability can change on click with no further request. What that array does not carry is an image, which is why the swap needs a second getProductPDPDetails call for the newly selected SKU — and, until the full image list ships, that call returns one hero image anyway. It also carries pdpUrl per variant, which is presumably the separate URL the open item refers to; we do not navigate to it.

10 — Deviations

Deviations

Variant options are authored, not read from the product record

Built

The Admin requirement has one hero SKU, with "the list of related variants" pulling dynamically from the API. We author the list instead: a row per buyable SKU, each carrying its own option values, with the option names set once at section level. Settled in the decision log under A variant section authors its SKU list in Amplience and hydrates it in one bulk call (2026-08-10), which rejected the API-driven path for three reasons. It cannot express "show four of these eight flavours, in this order", which is the difference between a merchandised landing page and a PDP. It depends on skuVariantFiltersConfigured, TVS-side data we neither own nor can check at build time. And the attribute-carrying path exists only on the PDP endpoint, which does not return onSale, so prices sourced from it would render fake strikethroughs.

Size has no API field, so it is authored too

Built

Flavour is served: flavor came back populated on the one real captured response. Size is not. weight and weightType read 1 and OZ on VS-8531, a tub the catalogue calls 11.01 oz., so the pair describes something other than pack size, and itemSize exists only on the PDP endpoint and has never been seen populated. Both are now registered with that warning attached. A reviewer checking whether a size pill matches the product record will not find a field to check it against.

The promo badge has no authored wording

Built

The Admin requirement gives Promo Badge + Message a 20-60 character count, which reads as two authored fields. Built as a single on/off toggle instead, with the badge and its note taken from the product record. A promo string is named explicitly among the things that are never authorable, alongside prices and quantity caps.
